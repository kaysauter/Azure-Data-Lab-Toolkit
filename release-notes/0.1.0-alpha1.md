# Azure Data Lab Toolkit 0.1.0-alpha1

1. Never run this against a subscription you care about.
2. Nothing here has ever been executed against live Azure. Not once.
3. `Start-AzureDataLabDeployment` creates billable resources. `Start-AzureDataLabTeardown` deletes resources.
4. The command surface and plan hashes may change without notice between alpha tags.

`Resume-AzureDataLabDeployment` can also submit a deployment that creates billable resources, and `Resume-AzureDataLabTeardown` also deletes resources. `Connect-AzureDataLabAccount` repeats the four warnings above before it signs in.

## What this release is

v0.1.0-alpha1 is the first alpha prerelease of Azure Data Lab Toolkit, a PowerShell 7.6 module that turns a YAML lab definition into a deterministic SQL Server on Azure VM plan. It covers the offline PowerShell foundation and the Azure-facing lifecycle: sign-in, live resolution, `-WhatIf` reconciliation, deployment, probes, and approval-gated teardown.

It is intended for contract review and local testing, not for production use. Every Azure-facing command is implemented and unit-tested with its Azure calls mocked, and none has ever run against a live subscription. In this project's status vocabulary nothing in this release is **Available**: that label is reserved for released, documented, and verified functionality, and nothing here has been verified against Azure.

## What it can and cannot do

Without Azure access, the module validates configurations, builds plans, exports them as JSON, Markdown, or standalone HTML, runs the browser configuration wizard, and keeps local run state and evidence.

`-WhatIf` reconciliation, deployment, probes, and teardown accept only configurations bound to the fixed `sqlvm-first-canary/v1` deployment profile: the `sqlvm-first-canary` template plus a `deploymentProfile` block carrying the profile ID and hash. The offline wizard (`Start-AzureDataLabConfigurationWizard`) produces such a configuration, `examples/sqlvm-first-canary.yaml` in the repository is one with placeholder values, and `Test-AzureDataLabDeploymentConfiguration` checks offline whether a configuration is eligible.

The deployment compiled from an eligible configuration creates a resource group; a virtual network with a network security group, two subnets, and a network interface; a Windows SQL Server 2022 VM (`Standard_D4s_v5`) with no public IP, and its SQL IaaS registration; and Azure Bastion Basic with its public IP. It reuses a Key Vault and a pinned version of the VM administrator secret in it. Both must already exist, and the vault must send its audit logs to the diagnostics destination the configuration names. The profile also requires a maximum run cost, a maximum runtime, and a time to live at least as long as that runtime.

Everything else is planning only in this release. The default `sqlvm-secure` template, which `examples/sqlvm-minimal.yaml` uses, can be planned but not deployed. A new Key Vault, a generated administrator password, a disk encryption set, catalog items, the Azure Files backup share, the backup-restore solution pack, and reused Bastion hosts or resource groups appear only in plans.

Every plan carries blocking findings; the unresolved marketplace image version is always one of them. A deployment is authorized only after live resolution, the first stage of the authenticated preflight (`Invoke-AzureDataLabPreflight`), has cleared all of them, and live resolution can clear only four: the image version, the reused Key Vault's compatibility, the pinned secret version, and the vault's audit diagnostics. Those four are exactly the blockers an eligible configuration's plan carries; a plan with any other blocker cannot be deployed.

Before you try the Azure path:

- Use an isolated subscription or a dedicated resource group with no other writers. Teardown deletes only the resources in its approved inventory, keeps the resource group, and stops before deleting while the group holds any resource outside that inventory.
- `cost.maximumRunCost` is an admission limit for the preflight's retail-price estimate, not an Azure billing cap.
- The configured runtime and time to live do not stop or delete anything. You remain responsible for teardown.

## Assets

- `AzureDataLabToolkit-0.1.0-alpha1.zip`: the module, laid out as `AzureDataLabToolkit/0.1.0/` for a PowerShell module path. It contains the module only: no examples and no dependencies.
- `AzureDataLabToolkit-0.1.0-alpha1.zip.sha256`: the zip's SHA-256 hash, in the format `sha256sum -c` reads.
- `sbom.spdx.json`: an SPDX 2.3 software bill of materials for the module, its six runtime dependencies, and its two build tools. Licenses are recorded as `NOASSERTION`. The SHA-256 checksum listed for each runtime dependency is the `packageDigest` recorded in the module's runtime dependency lock: it names the PowerShell Gallery package the lock was reviewed against, and nothing has verified it. What the module verifies is each installed dependency's `contentDigest`, measured from the files on disk.

The "Source code" archives GitHub adds to every release are the repository at this tag, not the packaged module.

## Checking the download

Download the assets from this page, or with the GitHub CLI:

```shell
gh release download v0.1.0-alpha1 --repo kaysauter/Azure-Data-Lab-Toolkit
```

Check the zip against its published hash. On Linux:

```shell
sha256sum -c AzureDataLabToolkit-0.1.0-alpha1.zip.sha256
```

On macOS:

```shell
shasum -a 256 -c AzureDataLabToolkit-0.1.0-alpha1.zip.sha256
```

In PowerShell, which prints `True` when the hash matches:

```powershell
(Get-FileHash ./AzureDataLabToolkit-0.1.0-alpha1.zip -Algorithm SHA256).Hash -eq (Get-Content ./AzureDataLabToolkit-0.1.0-alpha1.zip.sha256).Split(' ')[0]
```

The hash file comes from the same workflow run as the zip, so it catches a damaged download, not a tampered release. The attestations are what tie the zip to this repository's release workflow. Checking them needs the GitHub CLI signed in with `gh auth login`. This checks the build provenance:

```shell
gh attestation verify AzureDataLabToolkit-0.1.0-alpha1.zip --repo kaysauter/Azure-Data-Lab-Toolkit --signer-workflow kaysauter/Azure-Data-Lab-Toolkit/.github/workflows/module-ci.yml
```

Add `--predicate-type https://spdx.dev/Document/v2.3` to the same command to check the SBOM attestation. Both attestations have the zip as their subject; the hash file and `sbom.spdx.json` are not attested themselves, and the SBOM attestation carries the SBOM's content.

## Install

The [README at this tag](https://github.com/kaysauter/Azure-Data-Lab-Toolkit/blob/v0.1.0-alpha1/README.md) explains installation.

In short, you need PowerShell 7.6. Expand the zip into a folder on your `PSModulePath`. On Linux and macOS the module refuses to load while its scripts, lock files, or their folders are writable by group or others, so remove that write access if your umask grants it. The runtime dependencies, powershell-yaml 0.4.12 and five Az modules, are not in the zip: `Install-AzureDataLabToolkitDependencies.ps1`, in the module folder, installs the locked versions and checks their content. Then run `Import-Module AzureDataLabToolkit`. Leave the installed folder exactly as extracted: the packaged module lists every file in `build-provenance.json` and refuses to authorize a deployment once the folder no longer matches it.

## Commands

Offline: no Azure access and no Azure changes. `New-AzureDataLabRun`, the two export commands when given `-Path`, and the wizard write local files.

```powershell
Test-AzureDataLabConfiguration
New-AzureDataLabPlan
Export-AzureDataLabPlan
Find-AzureDataLabCatalogItem
Get-AzureDataLabSupportMatrix
Get-AzureDataLabTemplate
Start-AzureDataLabConfigurationWizard
Test-AzureDataLabDeploymentConfiguration
New-AzureDataLabRun
Get-AzureDataLabRun
Get-AzureDataLabEvidence
Export-AzureDataLabEvidence
```

Azure, read-only. These sign in, check the signed-in context, or read live Azure state, and the preflight also fetches public retail prices from `prices.azure.com`. None of them creates, changes, or deletes an Azure resource:

```powershell
Connect-AzureDataLabAccount
Test-AzureDataLabAzureContext
Resolve-AzureDataLabPlan
Test-AzureDataLabWhatIf
Invoke-AzureDataLabPreflight
Test-AzureDataLabDeployment
Resolve-AzureDataLabDeployment
Resolve-AzureDataLabTeardown
```

Azure, creating or deleting resources. `Start-AzureDataLabDeployment` and `Resume-AzureDataLabDeployment` submit ARM deployments that create billable resources; `Start-AzureDataLabTeardown` and `Resume-AzureDataLabTeardown` delete resources. Each requires an exact typed approval phrase:

```powershell
Start-AzureDataLabDeployment
Resume-AzureDataLabDeployment
Start-AzureDataLabTeardown
Resume-AzureDataLabTeardown
```

## Highlights

- Installable `AzureDataLabToolkit` module targeting PowerShell 7.6.
- Strict versioned YAML parsing and validation.
- Deterministic SQL VM plan creation with RFC 8785-style canonical serialization and SHA-256 plan hashes.
- Idempotency keys bound to toolkit, contributor, engine, and catalog revision contracts as well as resolved user intent.
- Field-level precedence and provenance for defaults, template, YAML, derived values, and flags.
- Explicit Key Vault, Bastion, identity, network, disk protection, licensing, cost, sensitivity, ownership, idempotency, approval, and teardown decisions.
- Fixed secure SQL VM alpha profile with typed desired properties, Azure API versions, Trusted Launch, Secure Boot, vTPM, host encryption, private networking, managed identity, disk layout, and SQL IaaS least-privilege intent.
- The locked `sqlvm-first-canary/v1` deployment profile, bound to a configuration by ID and hash, and its offline eligibility check.
- Azure Bastion Basic plan with a `/26` subnet, Standard static Bastion public IP, and no VM public IP.
- Planning only: an optional existing disk encryption set reference applied to every planned managed disk with fail-closed live compatibility requirements.
- Planning only: a private Key Vault plan with RBAC, purge protection, private endpoint and DNS, plus an explicit external-secret gate. `-GeneratePassword` records secure-generation intent in the plan only; nothing in this release generates a password, and deployment refuses that credential source.
- Planning only: metadata-only software and sample-data catalogs.
- Planning only: an optional Azure Files backup share with SMB OAuth, private endpoint and DNS, explicit VM identity authorization, no storage-account key, and an explicit blocker for the incomplete SMB OAuth guest client path.
- Planning only: a manual SQL VM backup-restore solution pack that derives a pinned dbatools dependency and plans a local restore-script render and a later staging step, preview-first and with database replacement refused. Nothing in this release renders, stages, or runs a restore script.
- Stable structured policy findings, deployment blockers, and plan-hash-bound acknowledgement requirements.
- Fail-closed resource-group reuse validation that binds the ARM ID to the configured subscription and resource-group name.
- Exact Azure type and subscription validation for reused Key Vault, Bastion, resource-group, and disk-encryption-set IDs, with a required Bastion reuse rationale.
- Scope-specific offline, Azure, and guest action preconditions and reconciliation sources.
- Collision-resistant storage-account and Key Vault truncation that preserves a deterministic 48-bit hash suffix scoped to normalized subscription and resource-group identities while keeping live collision checks fail-closed.
- JSON, Markdown, and standalone HTML plan export that first runs the full plan contract (the secret-free and plan-hash checks, schema and structure validation, and the intent and idempotency-key bindings) and never overwrites a file without `-Force`. Readable exports include desired properties, dependencies, RBAC evidence, and exact approval requirements.
- One read-only authenticated preflight that runs live resolution, native ARM What-If, a retail-price cost estimate, and a teardown preview.
- An offline browser configuration wizard that never accepts a password, token, or secret value.
- A dependency installer, shipped in the module, that installs the exact runtime dependency versions from the lock and checks their content.
- Linux, Windows, and macOS checks on every pull request that changes the module, and a release workflow that publishes only after those checks and its provenance checks pass.

- Pester: 423 passed, 1 skipped, none failed. Some tests run only on Windows and others only on Linux and macOS, so the skipped count depends on the platform.
- 80.06% command coverage (8,774 of 10,959 commands) against the 80% minimum the build enforces: a margin of 6 commands. Coverage is measured over the root module and the scripts in `Private/` and `Public/`; the provider, capability, and solution-pack plan scripts and the dependency installer are outside it. Windows runs different platform-specific code and skips different tests, so its figures can differ.

Every `./build.ps1 -Task All` run also requires:

- Zero PSScriptAnalyzer warnings or errors under the checked-in settings.
- Exact imports of the pinned Pester 5.7.1 and PSScriptAnalyzer 1.25.0 build tools and of the pinned powershell-yaml 0.4.12 runtime dependency.
- The checked minimal SQL VM plan hash, which Linux, Windows, and macOS must all reproduce.
- A clean import of the built module, with its exports compared to the manifest.

The release workflow ran that build on Linux, Windows, and macOS before publishing, and the zip attached here is the package its Linux run built. Every GitHub Action the workflows use is pinned to a full commit SHA. No build or test uses Azure credentials.

## Known issues

- **Live resolution cannot complete, so no deployment can be authorized.** The boundary that every Azure call passes through admits only cmdlets, but the locked Az.Resources 10.0.0 and Az.Monitor 8.0.0 export `Get-AzADUser` and `Get-AzDiagnosticSetting` as functions. Live resolution needs both, so its evidence can never pass: it reports "Key Vault audit diagnostics could not be verified." and "The signed-in deployment principal object ID could not be resolved.", and `Invoke-AzureDataLabPreflight` stops with "Azure Data Lab preflight failed at stage 'live-resolution'." The unit tests replace that boundary with a mock, which is why they pass. This has to be fixed before the first live run.
- `Export-AzureDataLabPlan` and `Export-AzureDataLabEvidence` resolve a relative `-Path` against the directory PowerShell was started in, not the current location, so after `Set-Location` the file lands elsewhere. Pass a full path.

## Not included

- Any verification against a live Azure subscription. Every Azure-facing command is implemented and unit-tested but has never been run for real.
- Deployment of anything outside the `sqlvm-first-canary/v1` profile.
- Guest setup, software installation, and database restore. The backup-restore solution pack only plans a manual, preview-first restore.
- Shutdown, and any automatic stop or teardown when the configured runtime or time to live ends.
- A Bicep or Terraform engine. `engine.type` accepts `bicep` and `terraform` in the configuration schema, but neither is implemented: `Test-AzureDataLabConfiguration` reports such a configuration invalid and `New-AzureDataLabPlan` refuses it. No terminal UI is planned; guided configuration is the offline browser wizard.
- An offline price cache. Cost estimation reaches `prices.azure.com`.
- A PowerShell Gallery package. This release is published only on GitHub.
- Production support or a production security baseline.

Catalog selections stay blocked for deployment until their integrity metadata is verified, and the deployment profile refuses them in any case.
