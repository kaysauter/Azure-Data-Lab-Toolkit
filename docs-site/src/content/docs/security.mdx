:::danger[Heavy development: no production security guarantee]
The current alpha authenticates to Azure, deploys real resources, and deletes
them, and none of that has ever run against a live Azure subscription.
`Connect-AzureDataLabAccount` signs in, and `Invoke-AzureDataLabPreflight` reads
live Key Vault, diagnostic-setting, marketplace-image, and VM-size state and
runs native ARM What-If. `Start-AzureDataLabDeployment` and
`Resume-AzureDataLabDeployment` create billable resources;
`Start-AzureDataLabTeardown` and `Resume-AzureDataLabTeardown` delete them by
exact resource ID and keep the resource group. These paths are unit-tested only.
The alpha is not production-ready and provides no production security baseline.
Never run this against a subscription you care about. A production release will
need a published threat model, supported baseline, limitations, and live test
evidence.
:::

<span class="status status-committed">Committed design</span>

Security decisions must be visible in the plan before Azure or a guest operating system is changed.

## Trust surfaces

| Surface | Main risks | Control intent |
| --- | --- | --- |
| Operator workstation | Command history, local files, cached tokens | Keep secrets out of YAML and logs; redact reports; use short-lived sign-in |
| CI runner | Untrusted pull requests, broad cloud access, retained logs | Protected environments, OIDC, least privilege, no cloud credentials on forked PRs |
| Azure control plane | Excessive RBAC, public endpoints, drift | Scoped roles, policy checks, private access where practical, Azure-aware `-WhatIf` |
| VM or container guest | Privileged installers, secret exposure, lateral movement | Minimize guest privileges, verify artifacts, probe installed state |
| Data and artifact sources | Tampering, malicious installers, unclear provenance | Pin versions, verify checksums or signatures, record owner and license |
| Run state and reports | Secret or sensitive-data leakage | Versioned schemas, redaction, access control, retention rules |
| Teardown | Deleting shared resources or leaving chargeable data behind | Ownership-aware deletion, confirmation, and cleanup proof |

## Secret-store decision for every solution

The committed baseline is Microsoft Entra authentication and [managed identities](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/managed-identity-best-practice-recommendations) where the target supports them. Every identity will receive only the permissions required for its operation. The plan must show the identity, scope, role assignments, and lifecycle before execution.

Every target provider and solution pack must emit exactly one
`secretStoreDecision`:

| Decision | Meaning |
| --- | --- |
| `deploy-key-vault` | Create an owned Azure Key Vault through the reusable capability module |
| `reuse-key-vault` | Use an existing vault without silently taking teardown ownership |
| `approved-external-store` | Use another approved store through an explicit adapter and policy decision |
| `not-applicable` | Record why the target or pack has no secret value to store |

[Azure Key Vault](https://learn.microsoft.com/en-us/azure/key-vault/general/secure-key-vault)
is the default Azure secret boundary, but the provider does not embed the vault
implementation. The Key Vault capability records Azure RBAC, network
restrictions, soft delete, purge protection, auditing, retention, ownership, and
teardown behavior.

Reused Key Vaults, Bastion hosts, resource groups, and disk encryption sets
must use exact, type-correct ARM resource IDs in the configured subscription.
The offline validator rejects a resource ID for the wrong Azure resource type,
a different subscription, or a create intent that also claims an existing ID.
Reused Bastion also requires a written administrative-access rationale.

:::caution[Key Vault diagnostics are a blocker the live preflight must clear]
The offline plan cannot verify Key Vault auditing, so it raises
`policy.secret-store.diagnostics-unresolved` as a **blocking** finding rather
than silently claiming that auditing exists. Authenticated live resolution
clears it by proving the diagnostic setting and its approved destination; until
it does, deployment authorization fails closed.
:::

The plan records the decision, and the design carries it into WhatIf, cost,
ownership, teardown, and security evidence; security evidence does not exist
yet. YAML, command history, normalized plans, run state, logs, and reports
contain references rather than secret values. `not-applicable` is never an
implicit default and always needs a recorded rationale.

Password creation and password display are separate high-risk choices:

- `-GeneratePassword` opts in to toolkit-side generation when an approved secret does not already exist.
- `-ShowGeneratedPassword` independently opts in to printing the value in the shell.
- one flag will never imply the other;
- both default to off, and non-interactive runs must make either choice explicitly.

:::danger[Password generation is plan intent only]
The current alpha does not generate a password. Before a PowerShell generator
can become available, it must use a cryptographically secure random source,
write directly to the approved vault, keep plaintext out of plans, state, and
logs, and pass an independent security review. A convenience generator based
on predictable PowerShell randomness is not an acceptable production control.
:::

Shell output can survive in scrollback, transcripts, screenshots, support bundles, and CI logs. Outside the one explicitly requested interactive display, redaction must remain active in terminal messages, JSON, Markdown, and HTML outputs.

## Administrative access decision for every VM

Public SQL, SSH, and RDP endpoints are not part of the intended default. A plan will show private endpoints, DNS, network security rules, operator access, and every requested public exception.

Every Azure VM must emit an `administrativeAccessDecision`. The default is
[Azure Bastion](https://learn.microsoft.com/en-us/azure/bastion/bastion-sku-comparison)
Basic with no VM public IP in the current alpha plan. The dedicated Bastion
public IP is Standard and static, and `AzureBastionSubnet` is `/26`. Reusing an
existing Bastion instance or opting out requires a rationale and explicit
approval. The plan records the decision, tier, any rationale, and any RDP rule
it implies. WhatIf and cost evidence can be produced only for the default,
because the one deployment profile pins `deploy-bastion` and Basic: WhatIf
classifies the Bastion subnet, public IP, and host, and cost evidence lists the
host and its IP as hourly charges that continue after VM shutdown. Reuse and
opt-out stay plan-only. The alpha cannot plan a
VM public IP, and release-gate security evidence does not exist yet.

Developer, Basic, Standard, and Premium tiers have different connection, scale,
peering, recording, and private-only capabilities. A provider requests the
Bastion capability; it does not implement Bastion internally. VM-hosted
containers inherit the same decision. Managed container platforms do not because
they do not expose a VM administrative surface.

## Execution and state

Protected interactive runs may use local state. CI, webhooks, or other
unattended mutation require encrypted remote state with authenticated locking,
monotonically increasing fencing tokens, resumable events, and short-lived OIDC
or managed-identity authentication. A local file lock cannot coordinate
independent runners safely.

## Sensitive data

`ContainsSensitiveData` is a required acknowledgement for real or restricted data. It is not a compliance certificate, a classification engine, or permission to bypass policy.

The acknowledgement will activate checks for permitted subscriptions and regions, encryption, key ownership, public access, diagnostic data, report redaction, backup and snapshot retention, access review, and deletion evidence. The organization that owns the data remains responsible for classification, legal basis, policy, and compliance.

## Artifact supply chain

Every downloadable tool, script, installer, backup, model, or private artifact needs:

- an authoritative owner and source;
- license and redistribution status;
- an immutable version or release identifier where available;
- a publisher signature or expected checksum where available;
- user-supplied checksum support for private paths and URLs;
- required execution privilege and compatibility;
- acquisition, installation, verification, and removal evidence.

A checksum mismatch must fail closed. Mutable URLs and artifacts without integrity evidence need an explicit warning and approval. Catalog inclusion is not an endorsement.

## CI identity

The committed GitHub design uses [OpenID Connect federation](https://docs.github.com/en/actions/concepts/security/openid-connect) instead of stored Azure client secrets. Trust conditions must bind the identity to the expected repository, branch or environment, and workflow context. Protected environments will gate live deployments and teardown.

## Repository and release controls

<span class="status status-current">Current</span>

Changes reach `main` only through pull requests. The `main` ruleset requires a
linear history and two checks, **Module checks** and **Docs checks**, which
report on every pull request. PowerShell analysis and Pester run in CI across
Linux, Windows, and macOS on every pull request that changes the module, its
tests or examples, the build script, the analyzer settings, `.editorconfig`,
`.gitattributes`, or a workflow file. The build loads
Pester and PSScriptAnalyzer only after checking them against a build-tool lock.

Releases are created only by the release workflow, when a `v<version>` tag is
pushed. After the three-platform checks pass on the tagged commit, a job with a
read-only token checks that the commit is on `main` and is the one those checks
tested, that the tag matches the manifest version, and that the package's build
provenance records that commit. It then writes the package's SHA-256 file and an
SPDX 2.3 SBOM. A separate job, which runs no repository code, attests the
package's build provenance and the SBOM and publishes the release with the
package, its `.sha256` file, and `sbom.spdx.json`.

The SBOM gives each runtime dependency the `packageDigest` from the runtime
dependency lock as its checksum. That value is recorded, not verified: it names
the upstream package archive the lock was reviewed against, and nothing in the
module or the release workflow hashes an archive to check it. The
installed-content guarantee is `contentDigest`, which the module measures from
the installed files and compares with the lock before it imports a dependency.

Private vulnerability reporting, secret scanning, and push protection are
enabled on the repository;
[`SECURITY.md`](https://github.com/kaysauter/Azure-Data-Lab-Toolkit/blob/main/SECURITY.md)
explains how to report a vulnerability. Dependency review, Dependabot security
updates, infrastructure scanning, and code and vulnerability scanning remain
backlog controls until they are enabled or their workflows exist and publish
evidence. See [Git And CI/CD](../git-and-cicd/).
