Security is a core planning concern, not a setting added after deployment.

## Identity and secrets

The intended baseline is:

- Microsoft Entra identities and managed identities where the target supports them;
- least-privilege Azure RBAC scoped to the operation;
- Azure Key Vault references instead of secrets in YAML, command history, logs, state, or reports;
- short-lived federation for CI/CD instead of stored client secrets;
- separate, explicit opt-ins for secret generation and secret display;
- redaction that remains active across terminal, JSON, Markdown, and HTML outputs.

Showing a password in the shell is a high-risk action because terminal history, transcripts, screen sharing, and CI logs can retain it. A future flag may permit this deliberately, but it must never be implied by another convenience option.

## Sensitive data

Real databases need stronger decisions than public samples. The planned `ContainsSensitiveData` acknowledgement will trigger policy checks for:

- permitted subscriptions, regions, and target services;
- encryption and key ownership;
- public access and private endpoint requirements;
- diagnostic data and report redaction;
- backup, snapshot, and temporary-copy retention;
- access reviews and teardown evidence.

The flag records awareness; it does not certify compliance or make an unsafe design acceptable.

## Network access and Azure Bastion

SQL and administrative ports should not be opened to the public internet by default. The provider should prefer private connectivity and explain any exception.

[Microsoft currently documents four Azure Bastion SKUs](https://learn.microsoft.com/en-us/azure/bastion/bastion-sku-comparison):

| Tier | Practical fit | Important trade-off |
| --- | --- | --- |
| Developer | Small dev/test lab in a supported region | Shared service, one VM at a time, no VNet peering; not for production |
| Basic | Dedicated host with fixed capacity | No advanced native-client, sharing, scaling, or recording features |
| Standard | Advanced connection features and configurable scaling | Dedicated hourly cost and public IP requirement |
| Premium | Compliance-sensitive administration | Adds session recording and private-only deployment |

The future schema should require an explicit tier or a documented default derived from the environment. Upgrades are possible, but Microsoft states that downgrades require delete-and-recreate; plans and cost reports must expose that consequence.

## Artifact supply chain

Every downloadable tool, script, installer, backup, or model should carry:

- authoritative owner and source URL;
- license and redistribution status;
- immutable version or release identifier;
- checksum or signature when available;
- user-supplied checksum support for private URLs;
- compatibility and privilege requirements;
- installation and removal evidence.

Downloads should fail closed when an expected checksum does not match. A catalog entry is not an endorsement, and an artifact must not inherit trust merely because it is popular.

## Security review workflow

Planned pull-request and release gates include secret scanning, dependency review, CodeQL, infrastructure-as-code scanning, vulnerability scanning, PowerShell analysis, Pester tests, and a documented threat-model review for changed trust boundaries.

See [Git And CI/CD](../git-and-cicd/) for the proposed automation.
