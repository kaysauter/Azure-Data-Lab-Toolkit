## Status labels

| Status | Meaning |
| --- | --- |
| **Current** | Verified repository or release behavior that exists now. Current does not necessarily mean deployable. |
| **Committed design** | An accepted architecture decision that is not yet implemented. |
| **Backlog** | Intended work whose implementation contract is not settled. |
| **Exploratory** | Research or an unresolved design question; it is not a promise. |
| **Deferred** | Work explicitly postponed to a later phase. |
| <span class="status status-available">Available</span> | Released, documented, and verified functionality. This label is reserved for release behavior. |

No deployment capability is currently marked **Available**.

## Plan and WhatIf

The committed design separates offline reasoning from live comparison. `-Plan` will validate configuration and explain resolved and derived values without Azure access. `-WhatIf` will require Azure context, compare that resolved plan with existing resources, and report create, reuse, update, replace, conflict, drift, or no-change without mutation. Neither command is implemented today.

## Target order

The order is deliberate. A later target should reuse tested core behavior instead of creating a parallel toolkit.

1. **SQL Server on Azure VM** - first end-to-end implementation and test target.
2. **Azure SQL Database** - first managed SQL target.
3. **Azure SQL Managed Instance** - managed instance networking and migration scenarios.
4. **Microsoft Fabric** - workspace and item creation plus guided target decisions.
5. **Azure Database for PostgreSQL** - managed PostgreSQL scenarios.
6. **SQL Server and PostgreSQL on Linux VMs and containers** - portable engine scenarios.
7. **Kubernetes** - deferred until container and lifecycle contracts are mature.

Azure Databricks and additional data platforms are tracked as future target providers. Git, storage, community tools, and related capabilities use their own extension types in the [Roadmap](../roadmap/).

## First implementation proof

SQL Server on Azure VM must prove one complete path: YAML validation, `-Plan`, `-WhatIf`, cost review, guarded PowerShell deployment, probes, evidence output, teardown preview, confirmed deletion, and cleanup proof.

## Source of truth

Use this order when sources differ:

1. Published releases and release notes define **Available** behavior.
2. The checked-in repository defines **Current** artifacts and verified development behavior.
3. Accepted architecture decisions define **Committed design**.
4. [`FEATURE_REQUESTS.md`](https://github.com/kaysauter/Azure-Data-Lab-Toolkit/blob/main/FEATURE_REQUESTS.md), issues, and the project board describe **Backlog**, **Exploratory**, and **Deferred** work.

The architecture is not proof of implementation, and the roadmap is not a delivery commitment. [Azure SQLVM Toolkit](https://github.com/kaysauter/azure-sqlvm-toolkit) is an unfinished predecessor; its features do not transfer automatically to this repository.
