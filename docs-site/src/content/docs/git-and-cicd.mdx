<span class="status status-backlog">Repository CI first; user-facing Git adapters follow before Fabric</span>

[GitHub](https://docs.github.com/en/get-started/start-your-journey/what-is-github)
and [GitHub Actions](https://docs.github.com/en/actions) serve two distinct
purposes in the roadmap:

1. **S2 repository engineering CI (FR-012)** checks Azure Data Lab Toolkit
   itself: package, PowerShell, Pester, schemas, docs, links, dependencies,
   secrets, vulnerabilities, and releases.
2. **S14 user-facing Git and CI/CD (FR-042 and FR-027)** expresses
   validate-plan-approve-deploy-probe-report-teardown intent for users, with
   GitHub as the reference adapter and
   [Azure Pipelines](https://learn.microsoft.com/en-us/azure/devops/pipelines/get-started/what-is-azure-pipelines),
   [GitLab CI/CD](https://docs.gitlab.com/ci/),
   [Gitea Actions](https://docs.gitea.com/usage/actions/overview), and
   [Forgejo Actions](https://forgejo.org/docs/latest/user/actions/reference/)
   as additional adapters.

The general adapter segment is scheduled after Bicep and Terraform and before
Fabric. That schedule is not a code dependency on either engine.

## Repository CI today

<span class="status status-current">Current</span>

Changes reach `main` only through pull requests. The `main` ruleset requires a
linear history and two checks from GitHub Actions: **Module checks**, the gate
job of `module-ci.yml`, and **Docs checks**, the gate job of `docs-checks.yml`.
A required check that never reports would block a pull request, so both
workflows run on every pull request. Their first job compares the pull request
with its merge base to decide whether the real checks are needed, and the gate
job passes only when those checks succeeded, or were skipped because the pull
request changed nothing they cover.

| Workflow | Runs on | What it does |
| --- | --- | --- |
| `module-ci.yml` | Every pull request; pushes to `main` that change `src/`, `tests/`, `examples/`, `build.ps1`, the analyzer settings, `.editorconfig`, `.gitattributes`, or any workflow file; `v*` tags; manual runs | Runs `./build.ps1 -Task All` with PowerShell 7.6 or later on Linux, Windows, and macOS: parser and PSScriptAnalyzer checks, Pester with the 80% command-coverage gate, build, and package. On a pull request, these checks run only when it changes one of those paths. A `v*` tag also verifies, attests, and publishes the release. |
| `docs-checks.yml` | Every pull request; manual runs | Builds the Astro site and the Slidev deck and checks internal routes and anchors. On a pull request, these checks run only when it changes `docs-site/` or one of the two docs workflows. |
| `deploy-docs.yml` | Pushes to `main` that change `docs-site/`, `CHANGELOG.md`, or the workflow; manual runs | Builds and link-checks the site, then deploys it to GitHub Pages |

### Releases

Releases are created only by `module-ci.yml`, never by hand, and each step runs
only after the previous one succeeds:

1. A maintainer merges a commit whose manifest carries the release version and
   which contains `release-notes/<version>.md` and a `## [<version>]` section in
   `CHANGELOG.md`, then pushes the tag `v<version>` on that commit.
2. The three platform checks run on the tagged commit.
3. **Protected release provenance** runs with a read-only token. It requires
   that the tag has the form `v<major>.<minor>.<patch>[-<prerelease>]`, that its
   commit is reachable from `main` and is the commit the platform checks tested,
   and that it equals `v` plus the manifest version. It requires exactly one
   tested package, named `AzureDataLabToolkit-<version>.zip`, laid out as
   `AzureDataLabToolkit/<ModuleVersion>`, and carrying build provenance that
   records that commit and version. It also requires a non-empty
   `release-notes/<version>.md` and exactly one `## [<version>]` section in
   `CHANGELOG.md`. It then writes the package's SHA-256 file and an SPDX 2.3
   SBOM.
4. **Publish release** runs no repository code. It attests the package's build
   provenance and its SBOM, confirms that the tag still points at the verified
   commit, and creates the GitHub release with `release-notes/<version>.md` as
   its body and three assets: the zip, its `.sha256` file, and
   `sbom.spdx.json`. A prerelease is marked as one and never becomes the latest
   release.

`<version>` is the manifest's `ModuleVersion`, followed by `-<Prerelease>` for a
prerelease, so v0.1.0-alpha1 is built from `ModuleVersion` 0.1.0 and
`Prerelease` alpha1.

## CI stages

| Stage | Required outcome |
| --- | --- |
| Validate | Parse PowerShell, validate YAML schemas and examples, check generated content |
| Test | Run unit, contract, fixture, failure-path, redaction, and report tests |
| Analyze | Run PowerShell, dependency, secret, IaC, and vulnerability checks |
| Build | Package the module and build docs without uncommitted generation |
| Plan | Produce deterministic plan and cost artifacts without Azure mutation |
| Compare | Run Azure-aware `-WhatIf` only in an approved environment |
| Deploy | Require protected-environment approval and scoped OIDC identity |
| Probe | Verify the target, data, tools, security posture, and expected outputs |
| Teardown | Preview, confirm, remove eligible resources, and publish cleanup proof |

## Security and quality gates

| Control | Planned use and boundary |
| --- | --- |
| [Dependabot](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain) | Update supported dependency manifests and GitHub Actions; updates still require review and tests |
| [Dependency review](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-review) | Show dependency changes and known vulnerability information in pull requests |
| [CodeQL](https://codeql.github.com/docs/codeql-overview/supported-languages-and-frameworks/) | Analyze supported languages only; CodeQL does **not** support PowerShell |
| [PSScriptAnalyzer](https://learn.microsoft.com/en-us/powershell/utility-modules/psscriptanalyzer/overview) | Static analysis for PowerShell style, compatibility, and selected defect patterns |
| [Pester](https://pester.dev/) | Exercise PowerShell behavior, contracts, negative paths, and redaction |
| [Checkov](https://www.checkov.io/2.Basics/CLI%20Command%20Reference.html) | Scan supported Bicep, Terraform, GitHub Actions, and related configuration when those files exist |
| Secret scanning | Detect committed credentials and block supported secret patterns |
| [Trivy](https://trivy.dev/docs/latest/guide/) | Planned generic scan for repository/filesystem dependencies and container images |

Today PSScriptAnalyzer and Pester run in `module-ci.yml`, secret scanning with
push protection and private vulnerability reporting are enabled on the
repository, and Dependabot opens version updates for GitHub Actions and the docs
site's npm packages. Dependency review, Dependabot security updates, CodeQL, and
Checkov are not enabled.

Trivy is the selected generic vulnerability scanner, but it remains backlog until a pinned workflow, severity policy, ignore process, database-update policy, and retained report exist. None of these tools proves that a deployment is secure.

## Cloud identity and approvals

Live workflows will use [GitHub OIDC federation](https://docs.github.com/en/actions/concepts/security/openid-connect) with least-privilege Azure roles. Trust policies must constrain repository, branch or tag, environment, and workflow context.

Protected environments will control deployment and teardown identities, required reviewers, and environment-specific configuration. Forked or untrusted pull requests will not receive Azure credentials or access to protected secrets.

CI, webhook, and other unattended mutation also requires encrypted remote run
state, locking, monotonically increasing fencing tokens, idempotency keys,
resumable evidence, and duplicate-trigger rejection. A workflow may resume an
approved run; it cannot approve its own plan, secret handling, spend increase,
sensitive data, adoption, or teardown.

## Live test protections

Live tests need explicit subscription and region allowlists, quota checks, constrained SKUs, unique ownership tags, concurrency limits, budgets, short TTLs, and cleanup that runs after failure. A final Azure query will record resources that remain.

Small SQL VM smoke tests can run after approval. Wider provider, engine, region, and version matrices belong on scheduled or release workflows. No workflow may delete a resource whose ownership is unknown.

## Fabric CI/CD is a later, separate segment

Fabric automation will follow the current [Fabric Git integration provider and item matrix](https://learn.microsoft.com/en-us/fabric/cicd/git-integration/intro-to-git-integration) and [Fabric CI/CD guidance](https://learn.microsoft.com/en-us/fabric/fundamentals/understand-best-practices-fabric-cicd). Full Fabric infrastructure-as-code parity remains exploratory.

Fabric workspace creation does not technically depend on Git. Fabric CI/CD does
depend on Fabric items and on a Git adapter that Fabric actually supports.
Completing GitLab, Gitea, or Forgejo adapters does not imply that Fabric accepts
those services.

Gitea and Forgejo can also become self-hosted lab solution packs, but that adds
storage, backup, identity, ingress, certificates, upgrades, scanning, secret
store, and teardown responsibilities beyond a pipeline adapter.
