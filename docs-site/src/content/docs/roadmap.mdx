The roadmap records **Backlog**, **Exploratory**, and **Deferred** work. It is not a statement of shipped behavior or a delivery commitment. Accepted architecture is **Committed design**; only published and verified release functionality is **Available**.

The authoritative backlog is [FEATURE_REQUESTS.md](https://github.com/kaysauter/Azure-Data-Lab-Toolkit/blob/main/FEATURE_REQUESTS.md). Work is tracked through [GitHub issues](https://github.com/kaysauter/Azure-Data-Lab-Toolkit/issues) and the public [Azure Data Lab Toolkit Roadmap](https://github.com/users/kaysauter/projects/6/views/1).

## Delivery sequence

```text
Architecture
  -> PowerShell module, YAML, flags, and provider contracts
  -> deterministic planning and run state
  -> assessment, security, cost, catalogs, CI/CD, and validation
  -> SQL Server on Azure VM reference provider
  -> storage, data onboarding, and software delivery
  -> Azure SQL Database
  -> Azure SQL Managed Instance
  -> Microsoft Fabric
  -> Azure Database for PostgreSQL
  -> Linux VMs and containers
  -> Kubernetes
```

This sequence controls delivery focus, not architectural coupling. PostgreSQL follows Fabric in the delivery order but does not depend on Fabric contracts. Bicep and Terraform both wait for stable normalized-plan and provider contracts; Terraform does not technically depend on Bicep.

## Phases

| Phase | Main outcome | Status |

| Foundation | Decision-complete architecture and reusable contracts | **Committed design** |
| SQL VM | First complete, tested lab lifecycle | **Backlog** |
| Azure SQL | Managed SQL Database and Managed Instance target providers | **Backlog** |
| Fabric | Guided workspace and item lifecycle | **Backlog**, with IaC aspects **Exploratory** |

## Plan before execution

The first implementation will distinguish two non-mutating review steps. `-Plan` resolves YAML, defaults, derived values, and intended actions offline. `-WhatIf` compares that plan with live Azure resources after sign-in. Both must produce reviewable evidence before deployment is enabled.

## First proof point

Success for the first implementation is not merely creating a VM. SQL Server on Azure VM must provide a complete, repeatable path from YAML through `-Plan`, `-WhatIf`, cost review, guarded PowerShell deployment, probes, HTML evidence, and confirmed teardown with cleanup proof.

Assessment work starts with Azure Arc and the migration component in SQL Server Management Studio. The exact privileges, billing, evidence, and automation boundaries remain to be settled before implementation.
