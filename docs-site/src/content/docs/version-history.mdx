- Slidev pitch deck for the vision, architecture, guardrails, and community invitation.
- GitHub Pages deployment workflow with a production-build internal-link gate.
- Status vocabulary that distinguishes Current, Committed design, Backlog, Exploratory, Deferred, and Available behavior.
- Security, licensing, cost, assessment, Fabric, catalogs, testing, and CI/CD architecture guidance.
- Clear extension boundaries for target providers, capability modules, catalog sources, solution packs, deployment engines, and probes.
- Separate offline `-Plan` resolution and Azure-aware, non-mutating `-WhatIf` comparison contracts.
- Roadmap metadata that separates technical prerequisites from delivery sequencing.
- Authoritative S0-S22 delivery segments with Contract, Live, and Release gates.
- First-class epics for the PowerShell engine, probes and evidence, Windows and
  Linux guest operations, SQL VM solution pack, remote state, PostgreSQL VM and
  container paths, Git/CI intent, Key Vault decisions, and Bastion decisions.
- Installable PowerShell 7.6 alpha with strict YAML validation, deterministic

- Offline commands for templates, catalogs, support matrices, planning,
  verified JSON, Markdown, and HTML export, and a browser-based YAML

- Azure sign-in, live resolution, native `-WhatIf` reconciliation, the

  approval-gated teardown.

  eligibility check.

  What-If, a retail-price estimate checked against the configured estimate

- Ownership-intent, idempotency, approval, teardown, Key Vault, Bastion,
  identity, network, disk-protection, licensing, cost, and sensitivity

- Fixed secure SQL VM desired-state profile with API versions, Trusted Launch,
  private networking, Key Vault credential binding, Bastion Basic, and SQL IaaS

- Manual SQL VM backup-restore solution pack with a pinned dbatools dependency,
  separate rendering and staging actions, and a preview-first restore contract.
- Structured blockers and plan-hash-bound acknowledgement requirements.
- Cross-platform module checks and local packaging. Before the tag, the suite

  80.06% command coverage, 6 commands above the

  `Install-AzureDataLabToolkitDependencies.ps1` script for the locked runtime
  dependencies, and a tag-driven release workflow that attests the package and

- Scope-aware offline, Azure, and guest action contracts with matching
  preconditions and reconciliation sources.
- A checked minimal-plan hash fixture for cross-platform determinism.
- Strict contributor metadata schemas and exact typed ARM ID validation for
  reused resources.

### Changed

- Corrected the Azure SQLVM Toolkit description to identify it as an unfinished predecessor and source of lessons.
- Aligned the assessment direction with Azure Arc and the migration component in SQL Server Management Studio.
- Clarified that architecture is committed design and roadmap entries are not shipped functionality.
- Reordered the roadmap so the managed, Azure VM, and containerized PostgreSQL
  paths, then Bicep, Terraform, and general Git/CI adapters, precede Fabric.
- Required a `secretStoreDecision` for every target and solution pack and a
  Bastion-first `administrativeAccessDecision` for every Azure VM.
- Separated repository engineering CI from the user-facing Git and pipeline
  capability.
- Reclassified S1 as implemented in the repository and recorded Azure sign-in,
  live resolution, `-WhatIf` reconciliation, the PowerShell deployment engine,
  post-deployment probes, and teardown as implemented and test-covered, without
  claiming a run against a live subscription or a passed Live or Release gate.
- Preserved deterministic storage-account hash suffixes when long lab names
  require truncation.
- Required the build to import its pinned Pester and PSScriptAnalyzer versions,
  and the module its pinned powershell-yaml version, explicitly.

### Current limitations

- The module is an alpha prerelease. The command surface and plan hashes may
  change without notice between alpha tags.
- Azure authentication, live `-WhatIf`, the PowerShell deployment engine,
  probes, local run state, and the teardown workflow are implemented and
  test-covered, but have never run against a live subscription.
- `Start-AzureDataLabDeployment` creates real Azure resources and
  `Start-AzureDataLabTeardown` deletes them.
- Guest execution remains a preview-first, user-executed contract; the toolkit
  runs nothing inside the VM.
- Selected catalog integrity and the default template's external secure input
  remain unresolved deployment blockers; the marketplace image version is
  resolved only by the authenticated preflight.
- No production security baseline.

The first implementation proof point is SQL Server on Azure VM from YAML through `-Plan`, `-WhatIf`, cost review, guarded deployment, probes, evidence, and confirmed teardown with cleanup proof.

Released entries link to the matching Git tag and GitHub release. Published releases and release notes define **Available** behavior only once it is verified, and nothing in 0.1.0-alpha1 is; repository implementation and tests define **Current** behavior; accepted architecture defines **Committed design**; the roadmap records **Backlog**, **Exploratory**, and **Deferred** work.

The repository-level log is maintained in [`CHANGELOG.md`](https://github.com/kaysauter/Azure-Data-Lab-Toolkit/blob/main/CHANGELOG.md).
